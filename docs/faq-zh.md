首页列出了七个问题。下面逐个回答，每题分两部分：**本项目（这个 sqlite 仿制品）实际做到了什么**，以及**真实 SQLite 是怎么做的**。凡是本项目代码里还没有的东西，都直接说没有，而不是假装已经实现。

---

## 1. 数据是以什么格式保存的？（在内存中和在磁盘上）

**磁盘上**：数据库就是一个由 4096 字节页组成的文件，第 `n` 页位于文件偏移 `n * 4096` 处。没有文件头，没有元数据页，没有页号映射表——页号就是偏移量。第 0 页固定是 B 树的根节点。

页内的布局由常量决定（`src/node.c`，常量值可用 `.constants` 元命令打印）：

| 区域 | 字段 | 大小 | 偏移 |
|---|---|---|---|
| 公共头部 | node_type | 1 | 0 |
| | is_root | 1 | 1 |
| | parent_pointer | 4 | 2 |
| 叶子头部 | num_cells | 4 | 6 |
| 叶子主体 | key | 4 | 10 |
| | value（序列化后的整行） | 291 | 14 |

一个单元格 = 4 字节主键 + 291 字节行 = 297 字节；头部 10 字节后剩 4086 字节，所以**一页最多 13 行**，装不下的零头直接浪费掉，绝不把单元格拆到两页。内部节点每个单元格是 4 字节键 + 4 字节子页号。

行在页里是紧凑排列的：id 4 字节，username 32 字节，email 255 字节，共 291 字节，没有对齐填充、没有长度前缀、字符串多余的字节是垃圾数据（`serialize_row` 只是按偏移 `memcpy`）。

**内存里**：同一个页就是一个 `malloc(4096)` 出来的字节数组，被 `void* pages[100]` 这个页缓存数组持有；访问时用指针算术把字节数组当成结构体读写的替代品。查询行时再用 `deserialize_row` 拷回 `Row` 结构体。所以内存和磁盘的格式基本一致，唯一的区别是页缓存里的页可能比文件中的新。

**真实 SQLite 的差别**：文件头 + `sqlite_master` 表（schema 存在页 1），每个表/索引是一棵 B 树，根页号记在 sqlite_master 里；页内有 cell pointer 数组、freeblock 链、碎片整理；记录使用 varint 头部和可变长 payload，超长记录会溢出到 overflow 页。本项目把这些全部省掉了，代价是 schema 硬编码、单表、定长字段。

## 2. 数据什么时候从内存移到磁盘？

**只有一处：`db_close()`**。它遍历 `0..num_pages`，对每个非空缓存页调用 `pager_flush`，把 4096 字节整页 `write` 回去，然后关闭文件。

除此之外没有任何时机：`get_page` 只在缓存未命中时把磁盘内容**读进**内存，从不回写；没有 dirty 标记，没有后台刷盘线程，没有 fsync，没有日志，页缓存满了（`TABLE_MAX_PAGES = 100`）也不做淘汰，直接越界。

后果很明确：进程正常 `.exit` 就持久化，被 `kill -9` 或断电就丢到上一次正常退出为止；写到一半崩溃会留下半页脏数据（`pager_open` 甚至会因为文件长度不是整页而直接报 "Corrupt file"）。

**真实数据库**：脏页在 checkpoint、缓存淘汰、或事务提交时写回；提交前要把日志落盘并 fsync，然后才允许把数据页写进主文件（SQLite 默认的 rollback journal 顺序是：写 journal → journal fsync → 写数据页 → 删除/重置 journal）。

## 3. 为什么每张表只能有一个主键？

因为**表本身就是一棵以主键为搜索键的 B 树**。键唯一决定了"这一行在哪个页的第几个单元格"，所以只能有一个键用来组织数据——这就是聚簇索引的本质。想让第二列也唯一，只能再建一棵 B 树（索引树），把该列的值映射到主键，而不是把数据再排一遍序。这也是为什么 SQL 语法上每张表只允许一个 `PRIMARY KEY`：多主键在这个物理模型里没有意义。

**本项目正是这个模型的裸版本**：`Table` 只有一个 `root_page_num`，插入时 `table_find` 按 `row->id` 定位，若该键已存在就返回 `EXECUTE_DUPLICATE_KEY`（第 9 部分），value 存的是整行。这里的主键和"数据所在的树"完全是同一个东西。

**一个容易踩的细节**：SQLite 中 `INTEGER PRIMARY KEY` 是隐藏 rowid 的别名，主键值直接存在 B 树的键里，不额外占存储；而 `TEXT` 或其他类型的主键实际上是"一张唯一索引 + 隐藏 rowid"，表本身还是按 rowid 排序。所以"一个主键"有时指的是"一个聚簇键"，有时指的是"一个唯一约束"。

## 4. 事务回滚是如何工作的？

**本项目没有事务**：`BEGIN/COMMIT/ROLLBACK` 都不认识，页是原地修改的，没有日志，也没有能力把已改动的页恢复到修改前。真要实现，缺的是三样东西：脏页追踪、修改前的页映像、以及一个原子的提交点。

**原理上有两条路线**：

- **undo（回滚日志）**：修改页之前，先把原始页拷到 journal 文件并 fsync，再改数据文件。回滚就是用 journal 里的前像覆盖回去；提交成功则丢弃 journal。崩溃后重启若发现 journal 残留，说明有未完成事务，重放前像即可。SQLite 默认就是这个模式。
- **redo（WAL）**：新值先顺序追加到 WAL 并 fsync，数据文件稍后才更新。回滚相当于丢弃 WAL 里未提交的记录；崩溃恢复时把 WAL 中已提交的记录重放到数据文件。

两者的共同前提是：**所有修改都发生在可丢弃的副本上，只有到达提交点才做一次原子性的切换**（切换的原子性靠日志记录的完整性校验，而不是靠"一次性写完所有页"）。内存里同样成立——先把改动落在页缓存副本并记下 undo，回滚时恢复副本，不让未提交状态污染已提交状态。

## 5. 索引是以什么格式保存的？

**本项目没有索引**，只有一棵表树。若要加，结构可以直接复用现有的节点格式：索引也是一棵 B 树，叶子存 `key + value`，区别在于 value 存**主键（rowid）而不是整行**；查到 rowid 后再回表树定位行——这就是"二级索引 + 回表"。内部节点与表树相同，只存键和子页号。

两个必须处理的设计点：

- **多列索引**：键不能只是一个 uint32，而是"列值序列 + 主键"拼成的复合键。末尾挂上主键是为了让键唯一，否则重复值（非唯一索引）无法区分先后。
- **叶子链表**：本项目已经用 `next_leaf` 指针把叶子串起来（`cursor_advance` 靠它跨页扫描），索引树同样需要它来做范围扫描。

**真实 SQLite**：表和索引共用同一个 btree 模块，靠 `intKey`（表，键是 rowid）和 `pPayload`（索引，键是记录）两个标志区分；索引记录里最后一列固定是 rowid。叶子之间同样有 next-leaf 链，数据只存在叶子（B+ 树变体）。

## 6. 全表扫描在什么时候、以什么方式发生？

**本项目**：每一条 `select` 都是全表扫描。`table_start` 先 `table_find(0)` 定位到最左叶子，然后 `cursor_advance` 逐个单元格前进，走完一页就沿 `next_leaf` 进入下一页，直到 `end_of_table`。没有 WHERE，没有范围下推，也没得选——不支持任何谓词。

**真实数据库里，这些情况会退化成全表扫描**：

- 谓词涉及的列上没有可用索引（最常见）；
- `LIKE '%abc'` 这种前缀通配，B 树索引排不上用场；
- 列被函数或运算包裹（`WHERE upper(name) = ...`），索引失效；
- `OR` 的某个分支无索引可用，整体只能顺序扫；
- 隐式类型转换导致索引键与比较值不可比；
- 需要按没有索引的列排序或做聚合；
- 优化器估算后发现顺序扫描比走索引+回表更便宜（例如范围很宽、或者命中的行占比很高）。

**方式**：从最左叶子开始，沿叶子链顺序读页（通常配合预读/批量 I/O），成本与行数成正比。按本项目每页 13 行算，扫一万行大约要读 769 个页；索引查找则是 O(log n) 次页访问，这就是差别所在。

## 7. 预编译语句（prepared statement）是以什么格式保存的？

**本项目**：没有真正意义上的预编译。`prepare_statement` 每次都从原始字符串重新识别关键字，产出一个栈上的 `Statement{ type, row_to_insert }`，执行完就丢。没有字节码、没有计划缓存、没有参数槽，也不存在跨连接的复用——本质上每敲一条 SQL 都重新"编译"一遍。

**真实 SQLite**：`sqlite3_prepare_v2` 把 SQL 编译成 VDBE（虚拟数据库引擎）的**字节码程序**，放在 `sqlite3_stmt` 结构里：一个 `Op` 数组、一组参数槽、若干游标和临时寄存器。它只存在于**进程内存**里，绑定在具体的数据库连接上，从不落盘；schema 版本（schema cookie）变化时会自动重新编译（`SQLITE_SCHEMA`）。PostgreSQL 的 plan cache 也是同样的性质——缓存的是内存中的执行计划，不是文件。

**为什么计划通常不落盘**：执行计划依赖 schema、统计信息和参数类型，数据一变就可能失效；字节码里还带着页号、游标下标这类运行时结构。能在磁盘上长期存在的，是 SQL **文本**（视图、触发器、sqlite_master 里存的建表语句），不是编译产物。

## 小结

这七个问题里，本项目真正给出答案的是第 1、2、6 题；第 3 题由"表即一棵 B 树"的设计间接回答了（尽管代码里没有 schema 概念）；第 4、5、7 题在本项目中是空白——需要一个 journal/WAL 层、一个独立的索引树、以及一套真正的字节码编译器才能回答。原作者在第 15 部分已经说明项目停止维护，所以这些空白是对照真实 SQLite 来补的。
